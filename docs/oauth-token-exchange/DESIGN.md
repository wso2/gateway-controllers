# Token Exchange Policy — Design Document

## What is the problem we are trying to solve?

Backends sitting behind the gateway frequently trust a different identity provider than the one that authenticated the client. A mobile app might authenticate to the gateway with a token from the organization's customer IdP, while the order-fulfillment backend it ultimately needs to reach only trusts tokens minted by its own internal authorization server. Today, API developers close this gap in one of a few unsafe or brittle ways:

- **Forwarding the client's original token upstream as-is.** The backend either has to be taught to trust a foreign IdP (expanding its trust boundary to every client-facing identity source), or the request is rejected outright.
- **Embedding a static, long-lived backend credential in the API configuration** (a shared client secret or service-account token baked into policy parameters or backend config) and attaching it to every request regardless of who the caller is. This collapses per-caller identity entirely — the backend can no longer distinguish one client from another, which breaks audit trails and makes it impossible to scope backend authorization to the original caller.
- **Writing bespoke, per-API mediation logic** (a custom interceptor service or hand-rolled policy) to call the backend's token endpoint, cache the result, and attach it to the upstream call. Every team re-solves the same problem — token-endpoint calling, response parsing, caching, failure handling, SSRF exposure — with varying degrees of correctness.

None of these are good: the first over-trusts the client's credential, the second erases caller identity, and the third is a maintenance and security liability multiplied across every API that needs it.

## Why should it be solved?

- **Zero-trust between gateway-managed segments.** The platform's security posture depends on each hop verifying its own trust relationship rather than inheriting one transitively. A backend should only ever see a credential its own IdP issued and vouches for.
- **No backend credential exposure to the client.** Whatever secret the gateway uses to obtain a backend token (`clientId`/`clientSecret`) must never be observable by, or derivable from, the client's own request or response.
- **Standards-based interoperability.** [RFC 8693 (OAuth 2.0 Token Exchange)](https://www.rfc-editor.org/rfc/rfc8693) and [RFC 7523 (JWT Bearer)](https://www.rfc-editor.org/rfc/rfc7523) are the established patterns identity providers already implement for exactly this delegation/impersonation use case. Building against the standard means the policy works with any RFC 8693/7523-compliant authorization server without custom integration work.
- **Consistent, centrally-maintained security properties.** A single, well-reviewed policy implementation means the SSRF hardening, response-size bounding, caching safety, and failure-closed behavior are solved once — correctly — and inherited by every API that attaches the policy, instead of being re-derived (or missed) by each team that would otherwise write this logic themselves.
- **Operational cost.** Without caching, every proxied request would require a synchronous round trip to an external token endpoint, adding latency and load to that authorization server on every single request.

## Proposed Solution

Introduce `oauth-token-exchange`, a gateway policy that:

1. **Reads the caller's existing credential** from a configurable location on the inbound request (`header` by default — e.g. `Authorization: Bearer <token>` — or `cookie` / `queryParameter`), taken from the live, kernel-mutated request state so that a rewrite performed by an earlier policy in the same chain (e.g. an auth policy that forwards a validated token under a different header name) is respected.
2. **Exchanges it at the backend's own token endpoint**, using one of two standards-based grant flows:
   - **TokenExchange** (default, RFC 8693): sends the caller's credential as `subject_token`, along with `audience`, `scope`, and `resource` (RFC 8707) parameters, and an optional `requested_token_type`.
   - **JwtBearer** (RFC 7523): sends the caller's credential as-is as the `assertion`.

   The gateway authenticates itself to the token endpoint with its own `clientId`/`clientSecret`, via `ClientSecretBasic` (HTTP Basic) or `ClientSecretPost` (form fields).
3. **Attaches the exchanged token to the upstream request** on a configurable header (default `Authorization: Bearer <token>`) — the backend sees only a credential its own authorization server issued; the client's original credential never reaches it.
4. **Caches the exchanged token in memory** for part of its reported lifetime (half of `expires_in`, floored at 30 seconds, and never allowed to reach or exceed the token's real expiry), keyed on a hash of the API, token endpoint, client ID, grant type, audiences, scopes, resources, and the caller's own credential — so repeat requests from the same caller under the same configuration reuse the cached token, while any change to those inputs produces a fresh exchange.
5. **Attempts the exchange optimistically at the header phase, but only defers the one failure mode that waiting can actually fix.** `OnRequestHeaders` defers to the body phase — recorded in `SharedContext.Metadata` as `deferred`, without rejecting — only when the subject token is missing, because it may simply arrive once an earlier body-phase auth policy runs. A subject token that *was* present but failed the exchange call, or a config that failed to parse, is rejected immediately with the header phase's own `ImmediateResponse` instead: repeating an identical call or re-parsing identical params would reproduce the same failure, so there is nothing to gain from waiting, and the rejection short-circuits the rest of the chain so the body phase never runs for that request.
6. **`OnRequestBody` only ever runs to resolve a deferred, missing-credential case.** Every other outcome was already handled — resolved or rejected — at the header phase. When it does run, it repeats the full extraction-and-exchange attempt and fails closed exactly as the header phase does: a missing subject token returns the gateway's unified `401` auth-failure response; an unreachable token endpoint, a non-2xx response, or a malformed response returns a generic `502` with its own fresh opaque tracking ID. The original client credential is never forwarded upstream as a fallback, and no internal detail (upstream error body, resolved host, stack trace) is ever surfaced to the caller.

This mirrors the existing `backend-jwt` policy's shape (attach a credential to the upstream request, cache it, fail closed) but differs in trust origin: `backend-jwt` mints a token signed by the gateway's own key, while `oauth-token-exchange` obtains a token the backend's own IdP issued and vouches for — the right choice whenever the backend's trust boundary is itself, not the gateway.

## Challenges and solutions

| Challenge | Solution |
|---|---|
| **SSRF via an attacker- or tenant-controlled `tokenEndpoint`.** The policy makes an outbound call whose target is operator-configured, not request-derived, but still needs the same dial-time protection as any outbound gateway call. | The outbound call goes through the gateway's shared, SSRF-guarded HTTP client — the same dial-time private/loopback/link-local/metadata-address denylist, bounded redirects, and timeouts used by every other policy-initiated outbound call — rather than a policy-specific, unguarded client. `tokenEndpoint` is also restricted to `https://` unless an off-by-default `allowInsecureTokenEndpoint` system override is enabled, per `ssrf-prevention.md`. |
| **Correct ordering against body-phase authentication policies, without giving up an early exit when possible.** Rejecting purely in the header phase would pre-empt a later, body-phase auth policy (e.g. `mcp-auth`, which only authenticates once it can parse the JSON-RPC method from the body) with a generic `401` before that policy ever got a chance to issue its own, more specific challenge — but running exclusively in `OnRequestBody` gives up the chance to resolve the exchange immediately when the credential is already present. | `OnRequestHeaders` makes an optimistic attempt and, when the subject token is missing, only *defers* (records `deferred` in `SharedContext.Metadata`, does not reject) — so an earlier-attached body-phase auth policy still gets to run and, if it forwards the credential, supply what the header phase couldn't find. This is the one case where deferring matters; every other outcome is resolved at the header phase itself (see below). |
| **Avoiding a doubled outbound call to the token endpoint on a deterministic failure.** If the subject token is present but misconfigured credentials (or a down token endpoint) make the exchange call fail, deferring that failure the same way a missing subject token is deferred would mean `OnRequestBody` repeats the identical, identically-failing call on every single request — doubling load on the token endpoint indefinitely until an operator notices and fixes the configuration. | `OnRequestHeaders` distinguishes the two failure modes: only a missing subject token defers; a subject token that *was* present but failed the exchange call (or an invalid config) is rejected immediately with `OnRequestHeaders`'s own `ImmediateResponse` — `502` with a tracking ID for an exchange failure, `500` for a config error. Returning `ImmediateResponse` from the header phase short-circuits the entire chain, so the kernel never buffers the body or invokes `OnRequestBody` for that request at all — not merely a cheap no-op, but no second call and no re-parse. |
| **Unbounded or malicious token-endpoint responses.** A compromised or misbehaving token endpoint could return an arbitrarily large or malformed body. | The response is read through a bounded reader (`maxResponseBytes`, default 64 KiB, operator-configurable) before any parsing is attempted; a response at or over the limit is rejected outright. |
| **Credential leakage into logs.** The caller's inbound credential and the exchanged backend token are both bearer secrets that must never appear in plaintext in logs, yet enough must be logged to debug a misconfiguration (wrong header name, missing prefix, wrong case). | Every log line that could carry a token value masks it to a short prefix/suffix (`maskToken`) per `authentication_authorization.md` GO-AUTH-003. Diagnostic logging on a missing subject token logs header *names* present on the request, never values, so an operator can tell a header genuinely never arrived from it arriving under an unexpected name/case. |
| **Caching correctness: never serving a token past its real expiry, and never leaking one caller's token to another.** | The cache TTL is derived as half of `expires_in`, with a 30-second floor applied only when that floor still fits strictly inside the real lifetime — it can never reach or exceed `expires_in`. The cache key folds in the caller's own credential (hashed, never stored in the clear) alongside the API and exchange configuration, so no two distinct callers — or two distinct configurations — can ever collide on the same cached token. |
| **A changed `cacheMaxSize` system parameter at redeploy time.** The underlying cache implementation fixes its capacity at construction. | The policy holds the cache behind a `sync.RWMutex` and swaps in a freshly constructed cache (discarding previously cached entries) whenever the configured `cacheMaxSize` differs from the cache currently in use, rather than attempting to resize in place. |
| **Choosing the right delegation flow for different backend IdPs.** Not every backend authorization server implements both RFC 8693 and RFC 7523, and policy authors need a single, explicit switch rather than protocol-detection magic. | `grantType` is an explicit, validated enum (`TokenExchange` / `JwtBearer`) with no runtime negotiation — consistent with `post-quantum-cryptography.md`/`authentication_authorization.md`'s broader principle of never letting a peer or a request dictate algorithm/protocol choice in a security-sensitive path. |
| **Preventing silent fallback to the client's own credential on failure**, which would quietly reintroduce the exact over-trust problem this policy exists to remove. | Every failure path in `OnRequestHeaders` and `OnRequestBody` returns an explicit rejection (`500`, `401`, or `502`); there is no code path in either phase that forwards the original subject token upstream when the exchange does not succeed. |
